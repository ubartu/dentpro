# Patient mobile implementation baseline

Recorded on 24 September 2026 following the request to consider the completed project work when implementing the mobile application. This is an implementation baseline, not a claim that the mobile application exists or that the API is production-ready.

## Implementation follow-through

The initial baseline below is retained as the planning record. `apps/mobile` now implements the patient UI and integrates with the existing panels. Patient accounts, eligible clinics, patient-safe appointment details, configurable capabilities and explanation failure states have been added. Versioned consent is recorded, while the broader production consent/retention lifecycle remains unfinished. See `implementation-status.md`, `verification.md` and `apps/mobile/README.md` for current completion and verification boundaries.

## Sources and decisions

- Product scope: `DENTpro_v1_5_Architecture.pdf`, especially pages 3–5, 7–9, and 12–13.
- Existing implementation: `services/api/dentpro/main.py`, `contracts.py`, `auth.py`, `operations.py`, and `worker.py`.
- Panel scope and previously recorded verification: `docs/implementation-status.md` and `docs/verification.md`.
- The PDF specifies React Native for patients, Next.js for clinic/admin, FastAPI for the shared backend, and `/apps/mobile` for the mobile project. Expo is a proposed implementation aid; it is not specified by the PDF.
- Target both iOS and Android from the React Native project. Reuse shared API contracts and backend workflows. Mobile screens need their own native UI.
- Preserve the separate clinic and admin web panels. Do not restore the removed patient web interface or introduce a patient-facing staff role switcher.
- Translation was explicitly stopped. Do not resume Turkish localization as part of mobile implementation without a new request.

## Patient journey and existing integration points

| Patient capability | Existing backend | Mobile implementation requirement |
| --- | --- | --- |
| Account and session | Staff authentication is persistent; patient access currently uses `/demo/session/patient` and one synthetic identity | Implement real patient identity and ownership isolation before real-user use. Keep any synthetic demo access explicitly development-only. Store session credentials using platform-protected storage and clear patient state on logout/expiry. |
| My cases | `GET /cases` scopes results to the patient | Show loading, empty, error, draft, shared and archived states; refresh after mutations and when returning to the app. |
| Create a case | `POST /cases` accepts title, region and affirmative consent | Present consent before submission. Current regions are Istanbul, Ankara and Izmir. Do not invent medical-history fields without extending the contract. |
| Upload X-ray | `POST /cases/{id}/xray`, authorized `GET /cases/{id}/xray` | Support PNG, JPEG and PDF selection/preview, permission errors, upload progress and retry. Images cannot change after sharing. Current storage is local; signed object-storage upload remains unfinished. |
| Choose clinics and share | `GET /clinics`, `POST /cases/{id}/dispatch` | Show region-appropriate eligible clinics, make recipients explicit and enforce server limits. Preserve existing recipients when showing additional sharing. |
| Read proposals | `GET /cases/{id}/proposals`, `GET /proposals/{id}` | Display source treatment items, FDI tooth numbers, material, prices, procedure sessions, total visits, availability, examination requirement and clinic notes. Use integer minor-unit money values and server-provided versions. |
| Read explanation | Included in proposal responses; worker runs asynchronously | Keep the clinic source visually separate from its explanation. Show pending state without blocking proposal access. Identify current template explanations accurately; they are not generated by a live LLM. Surface missing information, questions, disclaimer and glossary review status. Do not invoke explanation generation on screen views. |
| Compare | `POST /cases/{id}/compare` | Compare objective fields side by side. Show preliminary-price and differing-treatment-scope notices. Do not invent scores, sponsored placement, a best clinic, diagnosis or treatment recommendations. |
| Request callback/appointment | `POST /appointments` | Make clear this creates a request rather than an immediately confirmed booking. Refresh server state after uncertain responses; the current backend deduplicates requests per patient/proposal. |
| Track requests | `GET /appointments`; staff manage transitions in existing panels | Display requested, contacted, confirmed, completed and cancelled states. Extend the patient response to include safe scheduling/context fields before presenting confirmed visit details. |
| Receive updates | No notification delivery implemented | Add device registration and push delivery explicitly. Foreground refresh is not evidence that push works. Keep health data out of notification previews. |

## Preserve completed clinic/admin behavior

- A patient-created and shared case must appear in the selected clinic's inbox and in admin oversight using the same persisted records.
- Clinic drafts and internal notes remain private. Patient responses must not expose staff coordination notes or admin audit data.
- Clinic publication and revisions use the existing lifecycle: superseded, withdrawn and flagged proposals are withheld by the patient API. Refresh or invalidate mobile cached data after visibility changes; never keep an unavailable proposal actionable.
- Admin moderation, clinic suspension and case archiving remain server-enforced. Handle unavailable proposals, rejected dispatches and archived-case booking conflicts without bypassing checks.
- Appointment changes made in either staff panel must be visible to the patient. Do not build a parallel mobile appointment database.
- Clinic subscriptions are internal operational records. Do not add patient checkout or imply that fees have been collected. The PDF makes consumer access free and excludes referral commissions and sponsored ranking from v1.5.
- Keep explanation caching and immutable versioning on the server. Mobile must not send an X-ray, patient identifiers or contact details to an LLM. Automatic X-ray diagnosis/tooth mapping belongs to the separate optional v2 scope.

## Backend gaps confirmed during source inspection

1. **Patient identity:** `AccountInput` creates only clinic/admin accounts. Production patient signup, recovery and session management remain unimplemented; the synthetic patient endpoint does not provide multiple-user isolation testing by itself.
2. **Clinic eligibility:** `GET /clinics` currently returns every clinic and `ClinicOutput` has no active/accepting-cases field. Dispatch rejects inactive clinics. Provide a patient-safe eligible-clinic response so the selector can agree with that rule.
3. **Appointment details:** `AppointmentOutput` excludes `AppointmentDetail.scheduled_at` and clinic/case display context. Staff responses include these plus private notes. Add a dedicated patient-safe response rather than exposing the staff response wholesale.
4. **Limits:** upload and recipient limits are admin-configurable but lack a patient-facing configuration endpoint. Expose safe capabilities or implement accurate server-error handling rather than hardcoding limits that drift.
5. **Explanation failures:** the patient contract reports only `ready` or `pending`; the worker can stop after bounded failures or be paused. Provide an appropriate unavailable/retry-later experience without infinite loading or exposing internal job errors.
6. **Consent:** case creation records consent and dispatch records recipients/audit events. Production consent wording/version, recipient-specific evidence, withdrawal and retention workflows need review and implementation where required; an affirmative checkbox alone is not a complete lifecycle.
7. **External services:** signed storage, notification delivery and live LLM integration remain absent. Production startup is intentionally blocked. Do not remove that block merely to demonstrate the mobile client.

## Build and acceptance sequence

1. Scaffold `apps/mobile` for iOS and Android with environment-specific API configuration and shared contract usage. A physical phone cannot reach the development computer through the phone's `127.0.0.1`; document a reachable development endpoint.
2. Complete the no-AI marketplace journey against the existing API using synthetic data: create case, upload, consent/share, receive clinic proposals, compare and request callback/appointment.
3. Integrate the existing asynchronous template explanation and its pending/unavailable states. Add a live provider only as separately validated backend work; preserve template fallback.
4. Implement the patient-safe backend gaps above, real account lifecycle and push integration. Retest existing clinic/admin behavior after contract changes.
5. Verify on iOS and Android, then prepare test distribution and store release. Native builds, device tests, store accounts and review are separate deliverables; a successful web build does not prove native readiness.

Acceptance evidence must include:

- The mobile-to-clinic-to-mobile flow on both platforms, including persistence after restart and an appointment time confirmed in a staff panel.
- Separate patient accounts that cannot read or mutate each other's cases, images, proposals or appointments.
- Revised/withdrawn/flagged proposal handling, inactive clinic dispatch rejection and archived-case request rejection, including stale mobile screens.
- File permission denial, invalid/oversized uploads, offline/network failures, session expiry and uncertain request retries without accidental duplicate submissions.
- Explanation pending/failure handling with source proposals still readable, plus correct minor-unit currency and timezone display.
- Existing API and panel regression checks after backend changes, regenerated contracts when changed, native type/build checks and device/simulator evidence recorded with explicit unverified boundaries.

This baseline records requirements for subsequent implementation. No mobile code, backend behavior or localization was changed when creating it.
